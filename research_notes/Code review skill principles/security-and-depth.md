# Security, risk, adversarial, and quality-review principles

## Portable security and adversarial review steps

### Takeaway

The most portable security workflow is a dataflow-and-boundary review rather than a language-specific pattern scan: define the change and business context, identify assets/actors/trust boundaries, trace untrusted inputs to security-sensitive sinks, verify authentication/authorization and framework controls, then test abuse cases involving state, concurrency, retries, and side effects. Language/framework guides should be loaded only after the generic threat model identifies which sinks and protections are relevant.

### Cited Findings

- The Sentry security skill separates **reporting scope** from **research scope**: report only on the requested file/diff/component, but research the wider codebase to trace input origins, upstream validation, configuration, and framework protections before reporting. It explicitly rejects pattern-only findings. — [Sentry security-review SKILL.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SKILL.md#L17-L30)
- Sentry’s required candidate-finding checks are portable across stacks: confirm whether input is attacker-controlled, inspect validation/sanitization, determine whether values are deployment-controlled, and account for framework mitigations such as auto-escaping or ORM parameterization. — [Sentry security-review SKILL.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SKILL.md#L132-L166)
- A generic trust-boundary pass should cover request parameters, headers, cookies, uploads, message payloads, environment/configuration, command output, and third-party data; validation must be checked at the boundary and authorization at the authoritative server/service. — [Local security checklist](../../skills/evidence-based-code-review/references/security-checklist.md#L5-L17)

### Inferences

- A generic AI reviewer should represent each candidate issue as a tuple: **asset/impact, actor, trust-boundary source, transformation, sink, protection, reachability, and evidence**. This preserves the portable reasoning from the sources while allowing language-specific sink and mitigation lookups.
- “Threat modeling” can stay lightweight: list changed entry points, sensitive assets, identities/tenants, privileged actions, external systems, and new side effects; then enumerate the two or three highest-impact abuse paths. This is more practical than requiring a full formal model for every diff.
- The reusable security core should be policy-oriented (deny by default, least privilege, code/data separation, fail closed, minimize exposure, bounded resources, authenticated/encrypted transport) and should avoid converting every implementation example into a universal rule.

### Gaps

- The inspected sources do not define one shared cross-language taxonomy for assets, trust boundaries, exploit preconditions, and blast radius; the tuple above is an inferred synthesis from their dataflow, authorization, business-logic, and supply-chain guidance. — [Sentry security-review SPEC.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SPEC.md#L34-L57)
- Sentry’s bundled language coverage is Python and JavaScript/TypeScript; for Go, Rust, Java, and other languages it explicitly falls back to generic references, so a generic skill still needs a mechanism to inspect repository/framework protections rather than assume examples transfer directly. — [Sentry security-review SPEC.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SPEC.md#L19-L27); [Sentry security-review SPEC.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SPEC.md#L83-L88)

## Deep review without noise: risk, completeness, and uncertainty

### Takeaway

Depth is produced by disciplined scope expansion and adversarial tracing, not by reporting every suspicious pattern. The strongest controls are: gather business context, review only the requested change while tracing affected consumers, use a risk-based/conditional lens matrix, account for every changed file, separate confirmed findings from verification questions and recommendations, and keep low-confidence or cosmetic items out of the blocking report.

### Inferences

- A practical depth model should have three layers:
  1. **Always-on baseline:** exact scope/merge base, repository instructions, changed-file coverage, correctness, security boundary, compatibility, relevant tests/checks, and evidence/uncertainty reporting.
  2. **Risk-triggered deep pass:** threat model and abuse cases for public/auth/data/financial/privileged changes; dependency/CI pass for manifests, lockfiles, build scripts, workflows, or registry changes; migration/contract pass for schemas/APIs/queues; concurrency/idempotency pass for stateful or side-effecting code.
  3. **Opt-in strict pass:** architecture/code-quality restructuring, performance/load analysis, dynamic testing, fuzzing, or multi-reviewer orchestration.
- To control noise, a finding should need a minimal evidence chain: exact changed location, reachable path, attacker/user/environment control, missing or bypassed protection, concrete impact, and credible remedy. If one link is missing, use a “needs verification” item with the exact evidence required instead of a vulnerability claim.
- Completeness and concision are compatible: review every file, but report only high-conviction issues; the coverage summary proves what was examined while severity filtering protects reviewer trust.
- A “deep” review should not automatically mean “review the entire repository for pre-existing flaws.” The right boundary is changed code plus affected callers, consumers, configurations, feature gates, and deployment behavior needed to validate the change.

### Gaps

- The sources do not converge on one common severity vocabulary: Sentry uses confidence plus Critical/High/Medium/Low, Alibaba uses critical/high/medium/low and filters low, wshobson uses Critical/Should Fix/Consider, and the local skill uses Critical/Important/Minor. A generic skill should keep severity separate from confidence and define a stable mapping for verdicts. — [Sentry security-review SKILL.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SKILL.md#L32-L39); [Alibaba open-code-review SKILL.md](https://github.com/alibaba/open-code-review/blob/375f64cd6f67a48a135da83cfcf59c52669a09cb/skills/open-code-review/SKILL.md#L71-L73); [wshobson PR reviewer](https://github.com/wshobson/agents/blob/0874a27b17a22e2b7c2e2bcd725768e0803cad06/plugins/ship-mate/agents/review.md#L19-L47)
- The local report template has precise findings and “Not verified” sections, but it does not require a per-file coverage rate or an explicit reviewed/skipped checklist. — [Local report template](../../skills/evidence-based-code-review/references/report-template.md#L32-L62); [Alibaba open-code-review-delegate SKILL.md](https://github.com/alibaba/open-code-review/blob/375f64cd6f67a48a135da83cfcf59c52669a09cb/skills/open-code-review-delegate/SKILL.md#L121-L131)
- The local skill has an independent-review recommendation for high-blast-radius changes, but it does not prescribe independent dimensions, handoff artifacts, or overlap/coverage controls comparable to wshobson’s staged multi-agent workflow. — [Local SKILL.md](../../skills/evidence-based-code-review/SKILL.md#L82-L86); [wshobson full-review command](https://github.com/wshobson/agents/blob/0874a27b17a22e2b7c2e2bcd725768e0803cad06/plugins/comprehensive-review/commands/full-review.md#L106-L187)

## Conditional checks and gaps in the local generic skill

### Takeaway

The local skill is already stronger than a checklist-only reviewer: it is repository-aware, evidence-oriented, conservative, and covers correctness, security, compatibility, concurrency, tests, performance, architecture, UI, and rollout. The highest-value improvements are explicit threat modeling/risk tiers, conditional supply-chain and adversarial passes, changed-file coverage accounting, a stronger uncertainty/confidence contract, and an opt-in strict maintainability mode. These additions should be routing and reporting improvements rather than making every review run every specialized check.

### Cited Findings

- **Add a lightweight threat-model step.** The local workflow establishes scope and requirements, but it moves directly from repository discovery to applicable lenses. Add a compact risk summary before lenses: changed entry points, assets, actors, trust boundaries, privileged operations, external systems, feature gates, and blast radius. This recommendation is grounded in Sentry’s required dataflow/configuration research, Alibaba’s business-context input, and Cursor’s feature-gate/devex/side-effect guidance. — [Local SKILL.md](../../skills/evidence-based-code-review/SKILL.md#L32-L56); [Sentry security-review SKILL.md](https://github.com/getsentry/skills/blob/d12f250460ffd961f549dbebf7eeb0cf4afd4c2e/skills/security-review/SKILL.md#L24-L30); [Alibaba open-code-review SKILL.md](https://github.com/alibaba/open-code-review/blob/375f64cd6f67a48a135da83cfcf59c52669a09cb/skills/open-code-review/SKILL.md#L27-L32); [Cursor thermo-nuclear-review SKILL.md](https://github.com/cursor/plugins/blob/99b609a72323b70204eab407c622f436e858e112/thermos/skills/thermo-nuclear-review/SKILL.md#L22-L36)
- **Make the security confidence model explicit.** The local skill says to prefer verified findings and report uncertainty, but lacks the Sentry-style operational rule that a security finding needs a confirmed attacker-controlled source and that medium confidence becomes a verification question rather than a vulnerability. ### Inferences

- Recommended routing matrix:
  - **Always:** scope/merge base, repository rules, changed-file coverage, requirements/correctness, affected callers/consumers, relevant checks, finding evidence, uncertainty, verdict.
  - **Public/API/auth/data boundary:** threat model, authorization/object scope, injection, sensitive-data exposure, rate limits, error behavior, abuse cases.
  - **Stateful/financial/workflow/queue/concurrent:** state transitions, invariants, atomicity, idempotency, replay, races, retries, partial failure, resource exhaustion.
  - **Manifest/lockfile/CI/build/container/release:** dependency/supply-chain gate, secrets, install scripts, registry/source integrity, action pinning, permissions, artifact provenance, rollback.
  - **Schema/API/config/flag/deployment:** compatibility, old/new client behavior, migration and rollback, feature-gate leakage, devex and deployment order.
  - **UI/frontend:** XSS/DOM boundaries, accessibility, browser history/deep links, client-side auth assumptions, performance only when a workload or render path is affected.
  - **Large/high-blast-radius/explicit deep audit:** independent second pass, staged artifacts, strict maintainability review, dynamic/fuzz/load checks when available.
- Severity and confidence should be orthogonal. Example: a high-impact issue with incomplete reachability evidence is “High severity / Medium confidence / Needs verification,” not an asserted High finding; a confirmed low-impact issue can be “Minor severity / High confidence.”
- A review should communicate uncertainty in operational terms: what was checked, what was not runnable, which files were skipped and why, what assumption controls the conclusion, and the smallest next evidence step (caller, config, test, deployment contract, or runtime check).
- Dependency checks should be conditional because requiring full SBOM/CVE/license/provenance analysis on a UI-only change creates noise and cost; however, a changed dependency manifest or build pipeline should automatically widen the review because those files change the trust boundary.
- The local skill’s verdict categories can remain, but the report should include a compact “coverage and confidence” block so “Ready to merge” cannot be mistaken for “security proof.”
