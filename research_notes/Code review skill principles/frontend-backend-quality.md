# Code review skill principles

## How the reviewed skills organize categories and prioritize findings

### Takeaway

The repositories converge on an evidence-first, multi-axis review: establish scope and intent, inspect changed code with its consumers and contracts, route only relevant rule packs, verify with repository checks, and report concrete findings ordered by impact. The most portable design is a generic core with conditional backend/frontend packs rather than one universal checklist.

### Cited Findings

- Addy Osmani's skill uses five broad axes—correctness, readability, architecture, security, and performance—and starts by understanding the change context, reviewing tests, then reviewing implementation, categorizing findings, and verifying the author's verification story. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md)
- Gemini CLI's reviewer separates target resolution, preparation, in-depth analysis, feedback, and cleanup; its analysis pillars are correctness, maintainability, readability, efficiency, security, edge cases/error handling, and testability. [Source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/.gemini/skills/code-reviewer/SKILL.md)
- Dify's backend and frontend skills both require scope resolution, changed-code and contract tracing, evidence-backed findings, rule-pack routing, severity ordering, precise locations, failure paths, and concrete fix directions. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
- Dify uses path- and concern-based routing: backend reviews route models/migrations, architecture, repository access, or SQLAlchemy changes to separate packs; frontend reviews route accessibility, UI primitives, component architecture, data/query contracts, testing, performance, or code-quality changes to separate packs. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
- The strongest common priority rule is to lead with verified, high-impact findings and avoid speculative risks, praise-heavy reports, or cosmetic nits. Addy explicitly says to order by leverage with correctness/security first; Dify orders by severity and says impact, reachability, and recovery determine severity. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md)
- Severity schemes differ in names but are compatible: Addy uses required/critical/nit/optional/FYI labels; Dify uses P0-P3; the local skill uses Critical/Important/Minor. The portable invariant is an ordered impact scale plus an explicit distinction between blockers, actionable defects, recommendations, questions, and unverified areas. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md); [Source](../../skills/evidence-based-code-review/SKILL.md)
- Addy provides an unusual but useful structural heuristic: judge the resulting file size and changed-line size, split large changes, separate refactors from feature work, and prefer remedies that remove concepts rather than relocate complexity. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md)
- Gemini adds process discipline that is useful but should remain adaptable: review tests first, experimentally mutate a condition to see whether tests fail, review change descriptions, and inspect dependency changelogs and lockfile diffs for upgrades. [Source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/.gemini/skills/code-reviewer/SKILL.md)

### Inferences

- A generic skill should use a two-level taxonomy: always-on core lenses (scope, correctness, security, compatibility/API, failure/concurrency, tests, maintainability, performance, verification) plus conditional packs selected from changed paths, symbols, file types, manifests, and runtime behavior.
- Finding output should use one normalized severity vocabulary even if a repository uses another. A practical mapping is: Critical/P0 = severe security, privacy, data-loss, or broad outage; Important/P1 = primary workflow, authorization, contract, or release-blocking failure; Minor/P2-P3 = narrower concrete defects and actionable cleanup.
- “No issue found” should require a stated coverage boundary and verification evidence. A clean review is a claim about inspected scope, not proof that all risks are absent.

### Gaps

- The reviewed sources do not define a universal numeric formula for severity; impact, reachability, recovery, and repository conventions still require reviewer judgment. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
- Addy recommends mutation-based test verification but does not define a safe, stack-independent mutation procedure; this should be optional and bounded by repository tooling. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md)

## High-value portable checks across stacks

### Takeaway

The highest-value checks are contract and failure-mode checks that can be tied to a reachable scenario: requirements and edge cases, trust-boundary validation and authorization, compatibility across old/new data and clients, transaction/concurrency behavior, tests that would fail on regression, bounded resource use, reuse of canonical abstractions, and honest verification.

### Cited Findings

- Correctness checks should compare implementation with the stated spec, inspect null/empty/boundary/error paths, check race conditions and state consistency, and verify that tests assert behavior rather than implementation details. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/.gemini/skills/code-reviewer/SKILL.md)
- Security checks should identify untrusted inputs and external data, validate them at the destination-specific trust boundary, enforce authorization server-side, protect tenant/account/object boundaries, prevent injection, keep secrets and sensitive data out of logs and fixtures, and examine dependency/supply-chain risk. [Source](../../skills/evidence-based-code-review/references/security-checklist.md); [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md)
- Compatibility checks should cover old data, queued work, cached state, old clients, serialized formats, schema versions, optional fields, enum/nullability meaning, status/error shapes, pagination/sorting, retries/rate limits, deployment order, and rollback after new data has been written. [Source](../../skills/evidence-based-code-review/references/compatibility-checklist.md)
- Database and write-path checks should verify explicit commit/rollback behavior, short transaction windows, tenant scoping, appropriate ORM expressions instead of raw SQL, row-count/conflict detection, and a concurrency safeguard selected for the workload. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/sqlalchemy-rule.md)
- Performance findings should name a reachable workload and causal path: N+1 queries, unbounded fetches, missing pagination, serialized independent requests, hot-path heavy work, repeated renders/subscriptions, unbounded retries/polling/logging, or measurable bundle/render cost. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/performance.md)
- Maintainability checks are strongest when they identify a concrete structural cost: bypassing a canonical repository/helper, duplicate validation, a pass-through wrapper, feature policy leaking into shared code, unclear type boundaries, complexity relocated rather than removed, or a file/change too large to review safely. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/repositories-rule.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/code-quality.md)
- Test review should ask whether a test would fail if the change were reverted, whether expected values are independent, whether changed branches/errors/boundaries are covered, whether an outer contract or integration test is required, and whether the actual checks were run. [Source](../../skills/evidence-based-code-review/references/review-lenses.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/testing.md)
- Tests should be flagged as low value when they assert private implementation details, cosmetic classes, hook/effect structure, generic rendering, or mocked-away behavior; semantic queries and real feature boundaries are preferred when interaction semantics matter. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/testing.md)
- Dependency changes deserve changelog and migration-note review, isolated upgrades where practical, before/after green tests, lockfile-diff review, maintenance/license/vulnerability checks, and suspicion toward bulk “bump everything” changes. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md)

### Inferences

- A stack-neutral reviewer should treat “contract” broadly: HTTP/API contracts, persistence formats, queues/events, CLI/configuration, generated clients, component public APIs, accessibility semantics, and repository-defined architectural ownership all deserve the same evidence standard.
- The most reusable issue template is: precise location; triggering scenario; violated contract or invariant; concrete impact; evidence; smallest credible fix; and verification gap if the claim depends on unavailable runtime evidence.
- “Missing tests” should be a finding only when the changed behavior is regression-prone or externally reachable and the requested test would protect that contract. Coverage percentage alone is not enough.

### Gaps

- The reviewed sources mostly describe review heuristics rather than tool-independent ways to detect all of them. The generic skill should instruct the agent to discover the repository's own lint, type, test, build, migration, browser, and static-analysis commands rather than prescribe one tool.
- The backend packs are detailed for SQLAlchemy/Dify but should be translated into conditional concepts—transaction boundaries, tenant scope, ORM/query layer, repository boundary—rather than hard-coded framework checks for a generic skill. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/sqlalchemy-rule.md)

## When backend, frontend, testing, accessibility, and API lenses apply

### Takeaway

Lens selection should be evidence-driven and compositional. Apply backend lenses when the change reaches server handlers, services, domain logic, persistence, jobs, migrations, or external I/O; frontend lenses when it changes rendered UI, interaction, navigation, client state, browser data access, or shared UI primitives; apply both when a cross-boundary contract changes. Testing and API lenses are not tied to one directory and should be activated by behavior and contracts.

### Cited Findings

- Dify scopes its backend skill to `api/` and its frontend skill to `web/` or `packages/dify-ui/`, but both also require tracing consumers and contracts rather than relying on path alone. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
- Backend routing signals include models, migrations, controller/service/core/domain/library boundaries, repository/table access, SQLAlchemy sessions/queries/transactions, raw SQL, and concurrency-sensitive writes. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md)
- Frontend routing signals include semantics, naming, keyboard/focus, forms, pending states, responsive interaction, UI primitives, component ownership/props/state/effects/navigation, generated clients, queries/mutations/auth/SSR/URL state/persistence, tests, bundle/render/subscription cost, styling, and localized copy. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
- Accessibility applies to rendered behavior, not merely source attributes: inspect the final element semantics, accessible names/descriptions, keyboard reachability, visible focus, focus through async states, form submission/validation, overlays, reachability of essential content, long/localized text, viewport/zoom/forced colors, and reduced-motion behavior. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/accessibility-ui.md)
- Frontend data/API lenses should inspect generated operation readiness, deprecated markers, exact input/output types, query keys and cache policy, invalidation and retry behavior, authoritative auth/tenant decisions, SSR/dehydration, and whether URL/storage state has the correct owner and lifetime. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/data-query-contracts.md)
- Component architecture review should trace ownership and lifetime for state, handlers, navigation, focus, portals, dismissal, loading/empty/missing-data states, and public controlled-state contracts; file length alone does not prove a component-boundary defect. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/component-architecture.md)
- Backend architecture review should keep controllers responsible for parsing/calling/serialization, place business decisions in service/domain owners, keep domain code independent of request context, and keep business-agnostic libraries free of product policy. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/architecture-rule.md)
- Schema review should consider tenant ownership, duplicate indexes, dialect portability, cross-database migrations, and hidden cross-table queries in model properties because these can create isolation, write-cost, portability, or N+1 failures. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/db-schema-rule.md)
- API/contract review should be activated by changed routes, schemas, serializers, generated clients, event payloads, public types, configuration, or persistence formats, and should trace both producer and consumer behavior. [Source](../../skills/evidence-based-code-review/references/compatibility-checklist.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/data-query-contracts.md)

### Inferences

- Recommended routing decision tree:
  1. Always run scope, correctness, security/privacy, compatibility, failure/concurrency, tests, maintainability, performance, and verification triage.
  2. Activate backend if changed files or call graph touch server transport, business/domain code, persistence, schema/migrations, queues/jobs, external service calls, auth, or multi-tenant data.
  3. Activate frontend if changed files or call graph touch rendered output, components/primitives, keyboard/focus, forms, navigation, browser storage/URL state, client queries/mutations, SSR, or localization.
  4. Activate API/contract if any producer-consumer boundary changes, even if the diff is only frontend or backend.
  5. Activate accessibility whenever a user-facing interaction or rendered state changes; treat failures as correctness defects.
  6. Activate specialized testing checks when behavior, public contracts, error/recovery states, permissions, persistence, or a bug fix changes; skip test demands for mechanical/pass-through changes unless a contract is at risk.
- Path names are useful hints, not proof. Generated files, shared libraries, monorepo packages, tests, and configuration can carry cross-layer effects, so routing must be confirmed by imports/callers and the behavior owner.

### Gaps

- The local skill says to apply lenses selectively but does not provide an explicit trigger matrix or decision tree for backend/frontend/API/testing/accessibility activation. [Source](../../skills/evidence-based-code-review/SKILL.md); [Source](../../skills/evidence-based-code-review/references/review-lenses.md)
- Dify's path scopes are repository-specific and should not be copied literally into a generic skill. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)

## Gaps in the current local skill and recommended additions

### Takeaway

The local skill already has a strong generic review spine: exact scope, repository discovery, selective lenses, security and compatibility references, evidence-backed findings, verification reporting, review-only versus fix mode, and explicit verdicts. Its main opportunity is to add concrete conditional packs and routing signals from the reviewed repositories without losing its stack-neutral posture.

### Cited Findings

- The local skill already prioritizes requirements/correctness, security/privacy/authorization, data/API/persistence compatibility, failure/concurrency, tests, performance, architecture/reuse/maintainability, UI/accessibility, and operations/rollout; it also requires precise evidence and separates findings from recommendations, questions, and unverified areas. [Source](../../skills/evidence-based-code-review/SKILL.md); [Source](../../skills/evidence-based-code-review/references/review-lenses.md); [Source](../../skills/evidence-based-code-review/references/report-template.md)
- The local skill already includes broad security checks for trust boundaries, authorization, injection, secrets, sensitive data, dependencies, unsafe defaults, and rate limits. [Source](../../skills/evidence-based-code-review/references/security-checklist.md)
- The local skill already includes broad compatibility checks for old data, migrations, clients, APIs, queues, caches, deployment order, and rollback. [Source](../../skills/evidence-based-code-review/references/compatibility-checklist.md)
- Compared with Addy, the local skill lacks explicit tests-first review and bounded mutation testing, change-size/file-size heuristics, dependency-upgrade workflow, dead-code hygiene, change-description quality, and named structural remedies such as dispatcher extraction or deleting pass-through wrappers. [Source](https://raw.githubusercontent.com/addyosmani/agent-skills/main/skills/code-review-and-quality/SKILL.md); [Source](../../skills/evidence-based-code-review/SKILL.md)
- Compared with Gemini, the local skill does not explicitly distinguish remote PR preparation from local review, ask for manual/UI evidence where appropriate, or provide a compact author-facing severity taxonomy for required/optional/nit/FYI feedback. [Source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/.gemini/skills/code-reviewer/SKILL.md); [Source](../../skills/evidence-based-code-review/SKILL.md)
- Compared with Dify backend, the local skill lacks explicit generic checks for tenant predicates, transaction commit/rollback and window length, concurrency conflict detection, repository-boundary reuse, controller/domain dependency direction, model-property query avoidance, index redundancy, and dialect portability. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/sqlalchemy-rule.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/repositories-rule.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/architecture-rule.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/references/db-schema-rule.md)
- Compared with Dify frontend, the local skill's accessibility questions are broader but less operational: it does not explicitly require checking computed accessible names/descriptions, final composed semantics, focus continuity through pending/error/dismissal, form ownership and field association, overlay presence/dismissal, forced colors/zoom/localized content, or reduced motion. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/accessibility-ui.md); [Source](../../skills/evidence-based-code-review/references/review-lenses.md)
- Compared with Dify frontend data/query rules, the local skill lacks explicit checks for generated-client readiness and deprecated operations, exact DTO/type boundaries, cache keys/invalidation/retry policy, SSR hydration/revalidation, authoritative client/server auth, and URL/storage state ownership. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/data-query-contracts.md); [Source](../../skills/evidence-based-code-review/references/review-lenses.md)
- Compared with Dify frontend testing rules, the local skill does not explicitly distinguish valuable contract tests from implementation-detail tests, require semantic queries for UI, or limit test requests to reachable contract changes. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/references/testing.md); [Source](../../skills/evidence-based-code-review/references/review-lenses.md)

### Inferences

- Recommended additions, in priority order:
  1. Add a compact “lens activation” matrix to `review-lenses.md` with signals for backend, frontend, API/contract, database/migration, accessibility, testing, performance, and operations.
  2. Add a backend/data pack with generic equivalents of tenant scoping, explicit transaction boundaries, short transactions, conflict detection/idempotency, repository reuse, dependency direction, schema/index portability, and no hidden I/O in model properties.
  3. Expand the UI/accessibility pack with final semantics and accessible-name computation, keyboard/focus through async transitions, form/overlay contracts, localization/zoom/forced-colors/reduced-motion checks, and a rule that accessibility failures are correctness defects.
  4. Expand API/contract guidance with producer-consumer tracing, generated-client/schema readiness, exact type/nullability/enum behavior, status/error/pagination/rate-limit/auth compatibility, cache/query-key/SSR checks, and deployment/rollback order.
  5. Expand testing guidance with tests-first intent review, behavior-vs-implementation assertions, regression-test necessity, semantic UI queries, integration/contract boundary selection, and optional bounded mutation checks when the repository supports them.
  6. Add maintainability guidance for change/file size, complexity reduction, dead-code follow-up, dependency changelogs/lockfiles, one-purpose changes, and concrete structural remedies.
  7. Keep repository-specific commands and names in discovered local instructions; express all new rules as conditional concepts so the skill remains portable.
- Preserve the local report template's strengths—verification table, precise findings, “not verified,” questions/decisions, and assessment—while allowing reports to omit praise unless concrete strengths help explain a decision. This reconciles the local template with Dify's no-praise/no-speculation discipline. [Source](../../skills/evidence-based-code-review/references/report-template.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md)

### Gaps

- This research did not inspect repository-specific `AGENTS.md` files, implementation code, or live review examples beyond the linked skills and their bundled references; conclusions are about reusable skill guidance, not proof that every rule is enforced in the parent repositories.
- The reviewed Dify packs are intentionally scoped to Dify's paths and technologies, so any generic adaptation must avoid prescribing `api/`, `web/`, `packages/dify-ui/`, SQLAlchemy, React, or TanStack Query outside matching repositories. [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/backend-code-review/SKILL.md); [Source](https://raw.githubusercontent.com/langgenius/dify/main/.agents/skills/frontend-code-review/SKILL.md)
