# SQL and PostgreSQL code-review principles

## 1. Portable principles for a generic code-review skill

### Takeaway

The SQL skill contributes a reusable review *method*: inspect security, correctness/data integrity, performance, maintainability, and verification separately; require concrete evidence; and make findings actionable. The generic skill should retain those questions as technology-neutral lenses, while letting a database adapter supply SQL-specific tests and terminology.

### Cited Findings

- The SQL review skill organizes review around security, performance, code quality/maintainability, schema design, testing/validation, anti-patterns, a checklist, and a structured output format. This is a useful portable decomposition because the same review dimensions apply to non-database changes. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Its security guidance is broadly reusable: parameterize untrusted values, avoid string-built commands, apply least privilege and role-based access, protect sensitive data, audit sensitive operations, and review encryption. The database-specific manifestation is SQL injection, but the trust-boundary principle generalizes to shell, HTML, paths, templates, and other interpreters. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local security checklist](../../skills/evidence-based-code-review/references/security-checklist.md)
- The SQL checklist explicitly asks whether inputs are parameterized, permissions are appropriate, sensitive data is protected, joins are correct, predicates can use indexes, and subqueries are efficient. These are concrete prompts that can be translated into generic questions about input interpretation, authorization, resource use, and semantic correctness. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- The skill treats data integrity as something to validate, not merely infer from source: it gives checks for orphaned foreign-key references and invalid values, and separately recommends execution-plan review, realistic-volume load testing, concurrency/stress testing, and regression testing. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Its anti-pattern examples expose portable failure modes: N+1 work, using `DISTINCT` to hide a bad join, and applying a function to a filtered field in a way that defeats an index. The generic versions are repeated remote calls, deduplicating symptoms instead of fixing cardinality, and transforming data before a lookup instead of preserving a usable access path. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- The SQL output template requires a priority/category, location, issue explanation, security or performance impact when relevant, recommendation, before/after example, and expected improvement; it also asks for category scores and three priority actions. The reusable core is precise location + evidence + impact + smallest credible remedy. Numeric scores and “top three” can remain optional presentation choices. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local report template](../../skills/evidence-based-code-review/references/report-template.md)
- The local skill already establishes a stronger general workflow than the SQL source: define the exact change scope, discover repository instructions and normal checks, inspect callers/consumers/tests, apply only relevant lenses, report environmental failures separately, and avoid claiming safety merely because no issue was found. — [local review skill](../../skills/evidence-based-code-review/SKILL.md)
- The local report contract already requires severity, category, precise location, evidence, impact, and a credible fix, and separates findings from recommendations, unverified areas, and decisions. This should remain the generic reporting contract. — [local review skill](../../skills/evidence-based-code-review/SKILL.md); [local report template](../../skills/evidence-based-code-review/references/report-template.md)

### Inferences

- Add a database-aware verification branch to the existing workflow rather than importing SQL examples into the core skill. The core should ask: “What data, query, transaction, or schema invariant can fail; what evidence would distinguish a real defect from a suspicion; and what check was actually run?”
- Treat “evidence” as tiered: source inspection for semantic defects; an execution plan or measured workload for performance claims; representative old data and interrupted/repeated runs for migration claims; and a test or contract check for compatibility claims. This is a generalization of the SQL skill’s validation section and the local skill’s evidence bar. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md)
- Preserve a conservative severity model. The SQL skill labels injection as “CRITICAL,” while the local skill defines Critical/Important/Minor and maps Critical to release-blocking security, data-loss, or migration risk. The local taxonomy is more reusable; database guidance should provide examples for mapping database failures into it instead of introducing a second scale. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review skill](../../skills/evidence-based-code-review/SKILL.md)

### Gaps

- The SQL source does not define an explicit scope-establishment, repository-discovery, or “not verified” workflow; those should come from the generic skill rather than being inferred from a database checklist. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review skill](../../skills/evidence-based-code-review/SKILL.md)
- The SQL source recommends many checks but does not state how to choose among them based on changed files, deployment model, database engine/version, data volume, or available evidence. An adapter contract should make applicability and unavailable evidence explicit. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md)

## 2. Database-specific checks that belong in optional adapters

### Takeaway

PostgreSQL features should be a PostgreSQL adapter, not generic instructions. The universal SQL material is best represented as an optional relational-database adapter that supplies query, schema, migration, and transaction checks; the generic skill should invoke it only when database artifacts or persistence behavior are in scope.

### Cited Findings

- The PostgreSQL skill is explicitly scoped to PostgreSQL-only behavior and focuses on JSONB, arrays, custom types, PostgreSQL indexes, PL/pgSQL functions/triggers, extensions, Row Level Security, and PostgreSQL privilege syntax. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- PostgreSQL-specific query checks include using JSONB containment operators with suitable GIN indexing, array containment operators with GIN indexing, and validating JSONB structure with constraints. These cannot be core rules because the operators, index classes, and type semantics are engine-specific. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- PostgreSQL schema checks include `CITEXT`, `TIMESTAMPTZ`, enum types, domains, JSONB defaults, `BIGSERIAL`, and PostgreSQL `CHECK` expressions. These are useful recommendations only when the repository’s supported engine and version make them available and consistent with its portability goals. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- PostgreSQL performance checks include GIN/GiST selection, partition-key choice, window functions/CTEs, and PostgreSQL-specific functions. Function and trigger checks also include trigger firing conditions and PL/pgSQL error handling. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- PostgreSQL security checks include enabling RLS and writing policies with PostgreSQL session settings, restricting grants to specific objects, and reviewing extension use such as `pgcrypto`, `pg_trgm`, or `uuid-ossp`. The policy intent is portable; the SQL syntax and extension behavior are not. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- The SQL source’s vendor sections show why implementation adapters are needed: PostgreSQL JSONB/GIN and arrays, MySQL storage engines/InnoDB, SQL Server `DATETIME2`/columnstore, and Oracle sequences are different mechanisms for related goals. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Cross-engine SQL checks are still technology-specific relative to a generic code-review skill: parameterized query APIs, `SELECT *` exposure, joins and cardinality, SQL data types and constraints, index design, execution plans, and database role/function rights. They should be a relational/SQL adapter that can branch on engine and query layer, not assumptions embedded in every review. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)

### Inferences

- Define an adapter boundary with inputs such as database engine/version, migration framework, query library/ORM, changed schema/query files, and deployment topology. The adapter should return applicable checks, commands/evidence to seek, and engine-specific caveats; the core skill should consume the findings through the existing severity/report contract.
- Keep these portable *goals* in the core lens: no interpreter injection; least privilege; explicit data integrity; compatible reads/writes; bounded resource use; atomic and recoverable state transitions; and evidence for performance and rollout safety. Put syntax and mechanisms (`@>`, GIN/GiST, RLS policies, `sp_executesql`, InnoDB, sequences, etc.) in adapters. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- Adapter checks should be conditional rather than prescriptive. For example, “use an engine-appropriate index for the observed predicate” is portable within SQL review; “use GIN for this JSONB containment query” is PostgreSQL-specific and requires confirming query shape, data distribution, existing indexes, and supported version before reporting a defect. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md); [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md)

### Gaps

- Neither linked skill provides a version matrix, migration-framework adapter, ORM/query-builder adapter, or explicit rules for distinguishing “engine feature is available” from “engine feature is appropriate.” Those are necessary before turning examples into automatic findings. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- The PostgreSQL skill emphasizes feature usage (“leverage what makes PostgreSQL special”) but does not establish when portability, operational simplicity, or existing repository conventions should win. The generic skill should not treat use of a database-specific feature as inherently better. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md); [local review skill](../../skills/evidence-based-code-review/SKILL.md)

## 3. Gaps revealed in the current local skill and recommended additions

### Takeaway

The local skill already has the right evidence-first structure and broad lenses, but its database coverage is mostly a set of high-level prompts. Add a focused database reference that makes migration safety, query-plan evidence, transaction semantics, schema constraints, and database-specific applicability concrete without making SQL mandatory for every review.

### Cited Findings

- **Migrations and rollout:** the local compatibility checklist asks whether migrations are idempotent, resumable, observable, interruption-safe, and clear about indexes, constraints, defaults, backfills, and rollback limits. It does not explicitly ask about lock duration, online/concurrent index creation, table rewrites, long-running backfills, deployment sequencing for old/new application versions, dual-read/dual-write periods, or whether a failed step leaves a safe restart point. — [local compatibility checklist](../../skills/evidence-based-code-review/references/compatibility-checklist.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- **Query safety:** the local security checklist names SQL injection among injection classes and says validation must occur at trust boundaries, but it does not spell out parameter binding versus dynamic SQL, identifier allowlisting, stored-procedure `DEFINER`/`INVOKER` behavior, row-level authorization, or accidental sensitive-column exposure from `SELECT *`. The SQL source makes parameterization, least privilege, role-based access, sensitive data, and function rights explicit. — [local security checklist](../../skills/evidence-based-code-review/references/security-checklist.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- **Performance evidence:** the local performance lens asks for a named workload and evidence rather than intuition, but it does not name execution plans, realistic data volumes, join/cardinality checks, Cartesian products, function-wrapped predicates, over-indexing, or N+1 query detection. The SQL source supplies these concrete checks and calls for load, stress, and regression testing. — [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- **Transactions and concurrency:** the local correctness and failure lenses already mention check-then-write races, retries, idempotency, atomicity, transactions, locks, deadlocks, and recoverable state. They do not explicitly prompt for transaction boundaries, isolation level, lock acquisition order, deadlock retry policy, implicit/autocommit behavior, partial success across multiple statements, or database-specific DDL transaction semantics. — [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md)
- **Schema correctness:** the local compatibility material covers old/new reads, nullability, enums, identifiers, ordering, precision, encoding, time zones, defaults, and rollback. The SQL source adds explicit review of primary/foreign/check constraints, normalization, data types, default values, and referential/data-value integrity checks; these would strengthen the database reference. — [local compatibility checklist](../../skills/evidence-based-code-review/references/compatibility-checklist.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- **Reporting:** the local template is stronger on evidence boundaries and verdicts: it includes scope, checks, strengths, severity sections, recommendations, unverified items, questions/decisions, and an assessment. The SQL template usefully adds before/after examples and expected improvement for query findings, but its numeric “security/performance/maintainability/schema” scores are less defensible unless scoring criteria are defined. — [local report template](../../skills/evidence-based-code-review/references/report-template.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- **Severity:** the local skill maps Critical to security issues, data-loss risk, migration incompatibility, or release-blocking failures; Important covers merge-blocking defects or failed relevant checks; Minor covers localized follow-ups. The SQL source demonstrates a critical injection label but does not provide a complete, consistent severity policy. — [local review skill](../../skills/evidence-based-code-review/SKILL.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)

### Inferences

- Add a database reference with five conditional passes:
  1. **Query safety and authorization:** parameter binding, dynamic identifier allowlists, least privilege, stored-procedure execution rights, tenant/object boundaries, sensitive-column selection, and audit/encryption requirements.
  2. **Schema and data integrity:** primary/unique/foreign/check/not-null constraints, type/precision/time-zone semantics, defaults, normalization trade-offs, orphan/invalid-value checks, and index/constraint compatibility.
  3. **Migration and compatibility:** expand/contract sequencing, old/new application compatibility, backfill safety and resumability, lock/table-rewrite risk, index/constraint build strategy, interruption/retry behavior, observability, and rollback limits.
  4. **Query performance:** query plans, selectivity/cardinality, join conditions and type, predicate sargability, index coverage and over-indexing, bounded results/pagination, N+1 behavior, realistic data volume, and concurrency/load evidence.
  5. **Transactions and operations:** transaction boundary and isolation, atomicity across statements, lock ordering/deadlocks, retry/idempotency, autocommit/implicit transactions, timeout behavior, connection-pool use, and rollout/rollback observability. — These additions synthesize the concrete SQL checks with the local compatibility, failure, performance, and operations lenses. [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md); [local compatibility checklist](../../skills/evidence-based-code-review/references/compatibility-checklist.md)
- Add evidence requirements for database findings: cite the exact query/schema/migration location; include the relevant old/new contract or caller; use an execution plan or measurement for performance assertions; use representative fixtures plus repeated/interrupted migration runs for migration assertions; and mark engine/version/production-volume assumptions as unverified when they were not inspected. This extends the local “evidence before assertion” rule with the SQL skill’s execution-plan and load-testing expectations. — [local review skill](../../skills/evidence-based-code-review/SKILL.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Add database-specific severity examples while retaining the local taxonomy: Critical for injection, unauthorized cross-tenant access, destructive/data-loss migration, unrecoverable corruption, or a release-blocking lock/availability failure; Important for incorrect joins/cardinality, broken old/new compatibility, missing integrity enforcement, or evidenced major regressions; Minor for localized query clarity, missing explanatory comments, or low-risk index/constraint follow-ups. These are recommended mappings, not a claim that every instance has the same severity; impact and evidence still control the finding. — [local review skill](../../skills/evidence-based-code-review/SKILL.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Use the local report format as the default and add optional database fields only when relevant: engine/version, migration framework, affected tables/queries, plan or benchmark evidence, transaction/lock behavior, rollout order, and rollback limitation. Include before/after SQL only when it clarifies the smallest credible remedy. — [local report template](../../skills/evidence-based-code-review/references/report-template.md); [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md)
- Keep PostgreSQL checks in a separate adapter/reference: JSONB and array operators/indexes; GIN/GiST; `CITEXT`, `TIMESTAMPTZ`, enums, domains; partitioning; PL/pgSQL functions/triggers; extensions; RLS; and PostgreSQL grants. Activate them only after confirming PostgreSQL scope and repository conventions. — [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md); [local review skill](../../skills/evidence-based-code-review/SKILL.md)

### Gaps

- The linked skills do not provide enough operational detail to prescribe safe migration commands across engines. In particular, they do not document lock/DDL behavior, online schema-change mechanisms, isolation-level consequences, or rollback procedures; those must be supplied by a future engine/framework reference or explicitly marked as repository-dependent. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [PostgreSQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/postgresql-code-review/SKILL.md)
- Neither source gives a formal definition of “evidence sufficient for a performance finding.” The recommendation to require plans, measurements, and representative data is an inference from their testing guidance and should be calibrated to each repository’s tooling and data-access constraints. — [SQL code-review skill](https://github.com/github/awesome-copilot/blob/main/skills/sql-code-review/SKILL.md); [local review lenses](../../skills/evidence-based-code-review/references/review-lenses.md)
- The repository’s current evals include a database-migration case, but this research did not inspect its expected output in detail; future work should compare the proposed database reference against that eval before changing the skill. — [local repository layout](../../README.md)
